# Choose a researcher workflow

This index describes the public workflow bundles.
It separates scientific sources, methods and supported operations.
Use the static catalogue to select a guide before you select an environment or input.

A **workflow bundle** contains a guide and selected example/selector files for a task.
A **substrate** is the physical, numerical or reference process under investigation.
A **method** consumes evidence to produce a specified scientific quantity.
A **run** is one actual invocation or an issued operation with its own identity and records.
One bundle can use several methods or commands. Several bundles can share a substrate.
The directories are neither independent experiments nor a run archive.

## Discover without contact

```sh
uv run --no-sync empirical-lawhood workflow list --format text
uv run --no-sync empirical-lawhood workflow show rc-ladder-response --format json
```

These commands work without a project root, profile, network or optional native stack.
They inspect no source input or environment and build no provider.
The JSON joins command effects and invocation requirements from the CLI metadata owner.
`prerequisites_inspected: false` means availability has not been checked.
Discovery grants no authority or qualification.

The catalogue is installed in the wheel. Its guide/input locators belong to the selected
source checkout or source distribution. Obtain those files separately and pass explicit
paths when running an installed command. A wheel cannot assert a checkout's clean source identity.

## Complete workflow reference

The state describes the available operation, separately from its evidence ceiling.
Colour always accompanies a text label; a green operation grants no scientific qualification.

| State | Meaning |
|---|---|
| 🟢 Current operation | An integrated operation with its own declared result boundary |
| 🔵 Development authoring | A candidate can be authored; authoring alone does not issue it |
| 🟡 Development check | A bounded native, numerical or reference check |
| 🟠 Input check / transform | Only the named validation, inspection or transformation is available |
| ⚪ Deferred integration | Retained code without the stated public consuming route |
| 🟣 Historical result | Reported historical evidence without a current result route |

Mixed rows list each available boundary rather than assigning one optimistic state to the family.
Nested views do not increase independent-unit counts. Negative scientific results remain valid results.

## Configure, run and read

Start with the [reactor example](reactor-response/guide.md) for a public development report.
For an editable model, copy the input and follow [configuration](../docs/configuration.md).
Keep canonical consumer bytes separate from the edited original. Imports, authority records
and held plan/design bytes retain their own procedures.
Select only a command actually supported by the guide. Optional runtimes and authentic held
inputs are separate prerequisites, even when configuration validation succeeds.

Read [results and failures](../docs/results-and-failures.md). Retained development attempts,
candidate authoring files and issued receipts have different roles.
Use the [paper crosswalk](../paper/SOURCES.md#paper-studies-and-current-software) for all twenty-two reported study families.
Historical reproduction and new prospective studies have different protocols and evidence ceilings.
