# CLI reference

SPDX-License-Identifier: CC-BY-4.0

This reference gives information about the installed `empirical-lawhood` commands.
It gives command prerequisites and limits for the operator workflow.
Use it to find the required inputs for each command.

## Form an invocation

Use the [workflow catalogue](../experiments/README.md) to select a task procedure,
its input files and environment. This reference supplies command inputs,
effects, output conventions and refusal exits.

```sh
empirical-lawhood --help
empirical-lawhood workflow show rc-ladder-response
empirical-lawhood config validate --config /absolute/work/model.json --consumer rc-ladder-model --format json
```

From the selected locked checkout environment, prefix each invocation with
`uv run --no-sync`. The model path above must be your copied RC input; follow
[configuration](configuration.md) to obtain and prepare it. Use
`empirical-lawhood <group> <verb> --help` for conditional options.
Put global options before the group and command options after the verb:

```text
empirical-lawhood [global options] <group> <verb> [command options]
```

Commands have different output conventions: some print text or canonical
reports, and API commands can emit a JSON envelope with `--format json`.
Retained products require the selected command's explicit destination options.
The [results and exit codes](#results-and-exit-codes) tables below identify each
convention; [results and failures](results-and-failures.md) explains the files
and the permitted recovery action. Operational success and scientific support
are separate outcomes.

## Global inputs

`empirical-lawhood` is the only installed command.
If a command needs `--project-root` or `--operator-profile`, put these options before its group.
Put each optional trust or authoring option before the command group:

- `--dataset-projection-trust`
- `--approval-checker-trust`
- `--reactor-authoring-dir`
- `--circuit-authoring-dir`
- `--electron-gas-authoring-dir`
- `--synthetic-material-authoring-dir`
- `--authoring-dir` (closed current integration handoff)

These inputs do not grant scientific authority.
The CLI has no implicit home directory default for a trust path.

## Portable and source requirements

The wheel supplies help, the portable reactor example, document validation, static inspection, and family checks marked `none` below.
Install each selected native stack separately.
`doctor` can inspect an explicit storage profile without catalog creation.
The profile can be read-only.

The following checks have conditional requirements:

- prepared-response parent checks
- finite-response stage checks
- response-composition checks
- reactor prepared checks

Their preliminary refusals are portable.
For authenticated parent or upstream reads, use the selected project and guarded store.
Matrix-response child authoring also needs the target source.
Draft `campaign validate` is portable.
An executable package requires authority replay from the configured store.

Commands marked `target checkout` require that checkout to run its own tracked `src/empirical_lawhood` package.
A wheel has no claim to that checkout's clean Git implementation identity.
The clean tree, exact stored approvals, applicable native inputs, and authority are separate gates.

## Capability and evidence limits

A discoverable static capability descriptor can still require source data, native software, or authority for its executable binding.
The `list` and `show` commands do not read source bytes or grant readiness.
The reactor-prefix example is an unqualified native demonstration.
The separate RC-information example is an analytical construction with an
independent equation check, without sampled confirmation.
Resistor-capacitor, electron-gas and disclosed lattice-pairing method workflows
retain their target-owned candidate/provider routes.
The ambient-pressure material programme remains unqualified.

The [current paper integrations](integrations.md) include these implemented
operations. Their guides identify actual input producers and the next stage:

| Route | Current software operation | Scientific and access boundary |
|---|---|---|
| [RC challenges](../experiments/rc-challenges/guide.md) | Four independently authored canary, nomination, development and evaluation phases; issued execution, exact results and recovery | Numeric-source custody and exact preceding phase results; separate current issue, execution and applicable reveal authority |
| [Finite response law](../experiments/finite-response-law/guide.md) | Frozen nomination, current 32-root calibration/qualification and 64-root evaluation authoring, issued lifecycle and result joins | Fixed scientific operands, complete exposure census and current parents/grants; supplied sample seeds remain exposed |
| [Preparation applicability](../experiments/preparation-applicability/guide.md) | Ordinary D32/E64 screens, constructed Q8/E32 authoring/lifecycle and saved 24-root readiness | Unchanged OriginalF; exact current Q prerequisite for constructed E; protected reads require current grants |
| [Matrix scans and saved analyses](integrations.md) | Geometry and conditional-event development operations; current history/tangent acquisition; transient, baseline and preparation diagnostics | Development or outcome-visible analysis as stated by each family; exact complete inputs and custody, with current grants before protected diagnostics |

Authoring and no-contact provider/graph proof execute no scientific tasks and
create no authority. An implemented issued route still requires its actual
source, cohort, records and separately authorized operations. Current software
integration does not reproduce historical paper results or establish fresh
scientific qualification. Full scientific reruns remain separate work.

The following reference worlds supply only bounded native or truth-known reference checks:

- Brian2
- Cantera
- FiPy
- PyBaMM
- Grid2Op
- TORAX
- physical scale-morphism
- propulsion-reliability

The reactor batch command is a held-source preflight.
The prepared-response, information-response and causal-response held-input
candidate routes retain their nonpromotable development boundary. Prepared and
finite excluded canaries and finite calibration/stage input checks remain
bounded diagnostics beside the current integration routes above. An accepted
preflight or a new label supplies no missing scientific eligibility.

Glenn has retrospective local import and preview only.
Material control has held input wrapping and preflight only.
The Gym--TORAX native development check needs the target source checkout.
Candidate context is not automatically available for arbitrary substrates.

All commands use exit 2 for Click argument or option errors.
The following list gives the conventions:

- `api`: the common result-to-exit mapping in the following table.
- `refusal-3`: handled schema, input, prerequisite or native-check errors exit 3.
- `refusal-5`: handled authoring, source, integrity or storage errors exit 5.
- `invalid-2`: handled document or numerical-check input errors exit 2.
- `source`: missing `--yes` exits 3. Source authority failures exit 4. Custody or storage failures exit 5.
- `example-1`: demonstration failures, including an existing output directory, exit 1.

The following table applies only to the **common API envelope**:

| Exit | Meaning |
|---:|---|
| 0 | operation completed. Inspect its scientific verdict separately |
| 2 | invalid authoring or schema |
| 3 | missing readiness, prerequisite or write confirmation |
| 4 | authority missing or refused |
| 5 | identity, custody, integrity or storage guard refused |
| 6 | execution or recovery failed |
| 7 | requested object absent |
| 8 | immutable identity or concurrent-write conflict |

The `example reactor-prefix` command has its own simple text result.
It writes only to the required output directory.
It reports demonstration measurements.
It does not issue a campaign, an evidence receipt, or a law qualification.
